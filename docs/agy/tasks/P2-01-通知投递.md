## 约束

### 渠道

第二期先做两种，**驱动要能加第三种而不改路由与模板层**：

| channel_kind | 配置字段 |
|---|---|
| `telegram` | `bot_token`、`chat_id`、可选 `api_base`（反代） |
| `webhook` | `url`、`method`、`headers_json`、可选 `secret`（HMAC 签名） |

- ★ **`bot_token` 与 `secret` 走 `credentials` 表的信封加密**（`02-database.md` §3），
  **绝不明文入库、绝不进日志**。`logx.Redact` 已有，投递失败的错误信息必须过一遍
- 支持配置多个 Telegram 号（09 §3 明确要求），渠道之间互不影响
- ★ **出网请求必须带超时**（建议 10 秒）与**重试退避**（3 次，1s/4s/15s）。
  投递失败不许阻塞事件写入，也不许让 `Emit()` 变慢

### 路由

- 规则按 `event_type` 通配（`node.*`、`cloud.guard.*`）+ 最低级别过滤
- 一条事件可命中多条规则 → 投递到多个渠道，**按渠道去重**
- ★ **静默期（quiet hours）与去重窗口**：同一 `dedup_key` 在窗口内只推一次。
  保活模块每分钟跑一轮，没有这个会把人淹死

### 模板

- 模板是文件不是数据库行（09 §5），放 `internal/notify/templates/`，用 `text/template`
- 变量来自 `events.payload_json`
- ★ **模板渲染失败必须降级成「事件类型 + 标题」推出去，不许因为模板错就不推** ——
  丢告警比推得难看严重得多

### 投递记录

```
notify_deliveries(id, event_id, channel_id, state str(16),   -- pending/sent/failed
                  attempt i32, last_error text NULL,
                  created_at_ms, updated_at_ms)
```

界面上能看到「哪条事件推给了谁、成没成功、失败原因」。保留期 30 天，走已有清理机制。

### 测试渠道

★ 渠道配置页要有**「发送测试消息」按钮**，立刻能验证 token 对不对。
没有这个，用户配错了要等下一次真实告警才发现。

## 验收

1. 配一个 Telegram 渠道 + 一条 `node.offline` 的路由 → 拔掉 agent → **手机收到消息**
2. 故意把 `bot_token` 配错 → 投递记录里 state=failed 且 `last_error` **不含 token 明文**
3. 全仓库 grep：日志与 API 响应里**不出现 bot_token / webhook secret**
4. 同一 `dedup_key` 在去重窗口内连发 10 次 → **只推 1 条**
5. 静默期内的事件 → 入库但不推
6. 模板里故意写一个不存在的变量 → **仍然推出去**（降级为标题），不是静默失败
7. 关掉网络让投递全部失败 → `Emit()` 的耗时**不受影响**（写个基准测试证明）
8. Webhook 渠道对着 `httptest` 服务端验证 HMAC 签名正确

## 边界

- 不做邮件、短信、企业微信（加驱动即可，不在本任务）
- 不做告警引擎（`alert.*` 事件是 `07-monitoring.md` 的事，第二期后续）

### F1 · `internal/crypto` 与 P2-02 冲突（必须先合并再谈）

P2-01 与 P2-02 **各自实现了一份 `internal/crypto`，同包路径、API 不兼容**，
合并时 `internal/crypto/crypto.go` 与 `crypto_test.go` 直接冲突。

★ **这是任务拆分的失误，不是任一方的实现错误** ——
两个任务都被要求「密钥走 `credentials` 表的信封加密」，却没有指定由谁提供这一层。

**裁决：保留 P2-02 的实现，P2-01 改为调用它。** 理由：

| | P2-01 `Manager.Encrypt` | P2-02 `EncryptEnvelope` |
|---|---|---|
| 做法 | 直接用主密钥 AES-256-GCM 加密明文 | 每条记录随机 DEK 加密明文，再用主密钥包 DEK |
| 是否信封加密 | ❌ **不是**，只是单密钥加密 | ✅ 是 |
| 与 `02-database.md` §3 | 不符（规格写明「信封加密」） | 相符 |
| 密钥轮换 | 要重新加密全部记录 | 只需重包 DEK |

P2-01 的 `crypto.Mask()` 有用，**并进 P2-02 的包里保留**。

### 次要：列表信封不完整

`GET /api/v1/notify/channels` 与 `/rules` 只返回 `{items}`，
缺 `total`/`page`/`page_size`。`12-api-spec.md` §3 要求所有 GET 列表端点返回完整信封。
量小不影响使用，**并入 P1-27 的对账一起改**。
