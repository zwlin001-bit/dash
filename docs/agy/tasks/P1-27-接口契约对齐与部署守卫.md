## 背景：一次故障暴露的三个结构性问题

24/25/26 上线后，控制台整页崩在 `y.map is not a function`。

根因是 `web/src/api/nodes.ts` 里 `getGroups()` / `getTags()` **把分页信封当成了裸数组**：

```ts
// 服务端返回 {items:[…],total,page,page_size}
export async function getGroups(): Promise<NodeGroup[]> {
  return await apiFetch<NodeGroup[]>('/api/v1/node-groups');  // ← 拿到的是信封对象
}
// → Overview.tsx  groupList.map(...)  → TypeError，ErrorBoundary 接住，整页「加载出错」
```

★ **这个缺陷从 P1-17 就在，一直没被发现**，因为：
P1-22 加鉴权后所有请求都 401 → `catch { return [] }` 吞掉 → 页面看着「正常但空」。
**P1-24 把登录态修对，请求终于成功，缺陷才浮出来。**

已做的紧急修复（本任务开工时已在 main 上）：

| 文件 | 改动 |
|---|---|
| `web/src/api/nodes.ts` | 加 `toItems<T>()` 统一拆信封，`getGroups`/`getTags`/`getNodes` 全部走它 |
| `web/test/api_envelope.test.tsx` | 回归测试 |
| `scripts/lint-dist.sh` | 指纹计算锁定 `LC_ALL=C` |

## ❶ 全端点契约对账

★ **逐个端点核对「服务端实际返回」与「前端 TS 类型声明」是否一致**，
不是看类型标注写了什么，是看 `JSONSuccess(w, ..., X)` 里的 `X` 到底是什么。

产出一张对账表放进 `docs/12-api-spec.md`（或它引用的附录），每行三列：
**端点 · 服务端实际返回 · 前端声明**。三者不一致的全部改掉，**以服务端为准**
（除非服务端明显违背 `12-api-spec.md`，那就改服务端并同步改文档）。

已知的两处（可作为起点，但**不要以为只有这两处**）：

- `POST /api/v1/nodes/{id}/tags` 服务端返回 `{"ok":true}`，
  前端曾声明 `Promise<NodeTag[]>` —— 已在紧急修复里改对
- `GET /api/v1/events` 用 `{items,total,limit,offset}`，
  其余列表用 `{items,total,page,page_size}` —— **两套分页并存**

对 events 那处：**不要为了统一而改动线上接口**。
先在 `12-api-spec.md` 里把「events 用 limit/offset」写成明确契约（已标注），
是否统一放到第二期，本任务只要求**文档与代码一致**。

## ❷ 让契约不一致编译期就挂

光靠人对账，下次还会错。要有机制。

选一种做法，**在任务书回执里说明你选了哪种、为什么**：

- **A. 契约测试**：对每个列表端点写一个测试，断言「服务端 handler 的实际 JSON
  能被前端的解析函数正确消费」。Go 侧起 `httptest` 拿到真实 JSON，
  存成 fixture，前端测试读同一份 fixture 断言。
  **优点是真的能挡住，缺点是要维护 fixture。**
- **B. 从 Go 结构体生成 TS 类型**，前端不许手写列表响应类型。
  **优点是根治，缺点是引入代码生成步骤**，与「单二进制、少依赖」的取向要权衡。

★ 不接受「加注释提醒」这类做法 —— P1-25 的教训就是**靠人记住不可靠**。
