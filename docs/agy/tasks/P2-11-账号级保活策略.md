## 0. 先澄清一件已经做对的事

用户提出「阿里保活的机器和机器清单应该独立，各管各的」。
★ **核对结果：现在已经是独立的**，而且比原设计还彻底，**不要去动它**：

| | 现状 |
|---|---|
| `nodes`（机器清单） | 表里**没有** `provider_code` / `cloud_resource_id` 列，完全不知道云的存在 |
| `cloud_resources`（云资产） | 有 `node_id`，**可空**，是唯一的关联点且单向 |
| `guard_rules`（保活） | 挂在 `cloud_resource_id` 上，**从不碰 `nodes`** |

也就是说：一台阿里云 ECS 可以只在云资产里、不进机器清单（没装 agent 照样能保活）；
一台机器清单里的 VPS 也可以跟云资产毫无关系。两边各管各的，**关联是可选的增强**。

**本任务不改这个结构**，只补下面缺的那一层。

## 1. 真正缺的：账号级控制

现在 `guard_rules` 是**一资源一行**（`UNIQUE (cloud_resource_id)`），
只有单设备粒度。缺的是账号级。

★ **这不只是「少个功能」，是语义上就不对**：
CDT 流量配额**本来就是账号级的**（同一对 AK/SK 下所有实例共享一个数字，见 P2-02 §3）。
把阈值只挂在单实例规则上，用户会理所当然地以为每台机器有独立配额 ——
P2-04 §1 已经提醒「界面上必须说清楚」，但那是打补丁，正确做法是让模型跟现实一致。

### 表

```
guard_account_policies(cloud_account_id PK,
                       is_enabled bool,
                       actions_enabled bool,              -- 账号级总开关，false = 全账号只监控不动手
                       traffic_limit_gb f64 NULL,         -- 账号级 CDT 阈值
                       traffic_action str(16),            -- stop / notify_only
                       warn_ratio f64,                    -- 预警比例，默认 0.8
                       schedule_enabled bool,
                       schedule_start str(5) NULL,
                       schedule_stop  str(5) NULL,
                       schedule_tz str(64),
                       eval_interval_s i32,               -- 该账号的评估周期
                       created_at_ms, updated_at_ms)
```

`guard_rules` 加一列，用来表达「这台机器要不要跟账号走」：

```
guard_rules.inherit_account  bool DEFAULT 1
```

### 生效规则：账号是默认，设备是覆盖

★ **逐字段覆盖，不是整条覆盖。**

| 字段 | 取值 |
|---|---|
| `actions_enabled` | ★ **两级都为 true 才动手**（账号级是总闸，任一为 false 就只监控） |
| `traffic_limit_gb` | `inherit_account=1` 时用账号的；设备上填了值就用设备的（更严更宽都允许） |
| `schedule_*` | 设备 `schedule_enabled=1` 时用设备的，否则用账号的 |
| `warn_ratio` | 设备没填就用账号的 |

★ **`actions_enabled` 特意做成「与」而不是覆盖** ——
账号级总闸要能一键停掉整个账号的所有动作，这是出事时的急停按钮，
不能被某台机器的设置绕过。

### 决策优先级（在 P2-04 §2 的基础上加一层）

```
账号级 is_enabled=false          → 整个账号本轮跳过
账号级 actions_enabled=false     → 照常评估、照常告警，但不执行任何启停
设备级 is_enabled=false          → 该设备跳过
其余                              → 走 P2-04 已有的「日程 > 流量 > 保活」
```

★ **P2-04 §2 的四条安全性质一条都不许放松**，尤其：
「计划关机只依赖 ECS 状态可读」「读不到流量不许启动」在账号级同样成立。

## 2. 账号与凭据的录入

用户要的是「输入账号 + 对应的 access 来控制」。P2-02 已经有 `cloud_accounts` + `credentials`，
本任务只补录入体验：

- ★ **一步录完**：填账号名 → 填 AK/SK → 选归属地（中国站/国际站）→ 选 region →
  **立刻做一次 `provider.healthcheck` 验证凭据可用**，不可用就别存
- 存完自动跑一次 `resource.list` 发现实例，列出来供勾选纳管
- ★ **AK/SK 明文只在这一次请求里存在**，走 P2-02 的信封加密，
  之后任何接口只返回掩码指纹（`LTAI****3f2a`）
- 一个账号可以配多个 region；★ **CDT 流量仍然是整个账号一个数**，界面上要写明

## 3. 界面

守卫页改成两层：

```
账号卡片（可折叠）
├─ 账号名 · 凭据指纹 · 归属地 · 健康状态
├─ ★ 账号级 CDT 用量进度条（已用 / 阈值），这是账号下所有实例共享的
├─ 账号级开关：is_enabled / actions_enabled / 阈值 / 日程
└─ 实例列表
   └─ 每台：状态 · 指标 · 「跟随账号 / 自定义」切换 · 自定义时才展开设备级设置
```

- ★ **设备行上要显示它当前生效的值来自哪一级**，
  比如阈值旁标「继承账号」或「设备覆盖」。不标的话用户永远搞不清为什么某台机器行为不一样
- 账号级 `actions_enabled=false` 时，★ **整个账号卡片显示醒目的「仅监控」横幅**，
  设备级的开关全部置灰并说明原因
- 颜色走 token（`lint-css-tokens` 会拦）

## 4. 事件

沿用 P2-04 已登记的 `cloud.guard.*`，`payload_json` 里**加一个 `decided_by` 字段**
（`account` / `resource`），说明这次动作是账号级还是设备级配置决定的。
排查时这一个字段能省很多事。

`dedup_key` 账号级事件用 `guard:acct:<account_id>:<event_type>:<月份键>`。

## 验收

1. 只配账号级策略、设备全部 `inherit_account=1` → 保活正常工作，行为与账号设置一致
2. ★ 某台设备设自定义阈值 → **只有它按自己的阈值走**，同账号其他机器不受影响
3. ★ **账号级 `actions_enabled=false`** → 即使某台设备自己是 `true`，
   **也不执行任何启停**；事件与告警照常
4. 账号级 `is_enabled=false` → 该账号整轮跳过，不产生任何云 API 调用（日志可证）
5. 设备行上正确显示「继承账号 / 设备覆盖」，与实际生效值一致
6. 录入新账号时凭据不可用 → **拒绝保存**并给出明确错误，不留半条脏数据
7. 存完账号后任何 API 都读不出 AK/SK 明文，只有掩码指纹
8. ★ **P2-04 的四条安全性质在账号级依然成立**：把 CDT 权限去掉 →
   计划关机照常执行、不许启动任何实例
9. 事件 `payload_json` 里有 `decided_by`，取值与实际决策来源一致
10. 一个账号跨 3 region 20 台实例 → **CDT 调用仍是 1 次**（P2-02 §3 的约束不许退化）
11. `make lint`（含 SQL 方言与 CSS token）、`make test` 全绿
