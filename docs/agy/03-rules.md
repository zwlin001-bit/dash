# 通用工程约定

**每个任务都适用。派发时不再重复，但验收时逐条检查。**

---

## 1. 语言与版本

- Go **1.22+**，`go.mod` 里锁定一个具体版本，不许各任务各改
- 前端用 TypeScript
- **代码注释、提交信息、PR 说明用中文**；标识符、字段名、错误码、日志 key 用英文
- 文档用中文

## 2. 依赖纪律

**这个工程的价值有一半在「轻」上，依赖必须克制。**

- **agent 侧（`agent/`、`cmd/dash-agent`）：新增任何第三方依赖都要先上报，不许自行引入。**
  目前允许的只有 WebSocket 库一个。**gopsutil 及同类库是明令禁止的**
- 服务端新增依赖要在 PR 说明里写明：为什么标准库做不到、评估过哪些替代
- 不引入「为了少写十行代码」的工具库
- 依赖必须锁定具体版本，不用 `latest`

## 3. 测试

- 每个任务至少覆盖：**正常路径 + 一个失败路径 + 一个边界条件**
- 解析类代码（`/proc`、协议、SQL 构造）必须有单元测试，**用真实样本数据**
  （比如 Alpine 上真实的 `/proc/meminfo`，不要自己编一个理想格式）
- 涉及数据库的测试跑在 docker MySQL 8 上，Oracle 侧至少手工验证一次并在 PR 里贴输出
- **不追求覆盖率数字**，追求「这个 bug 会不会被测试抓到」
- `make test` 必须能在干净环境一条命令跑完

## 4. 日志与错误

- 日志写 stderr，结构化（key=value 或 JSON），**不自己做文件轮转**
- **日志和错误信息里永远不出现**：密码、token、wallet 密码、主密钥、云厂商 AK/SK。
  统一走 T0.4 提供的 redact 辅助函数
- 错误一律 `fmt.Errorf("...: %w", err)` 包装，保留链路
- **不允许吞掉错误**（`_ = doSomething()`）。确实要忽略的，写注释说明为什么

## 5. 不许碰的文件

| 文件 | 说明 |
|---|---|
| **`docs/` 下的全部文件** | ★ **AGY 一律不提交。** 需要改设计就在 PR 说明里写清楚要改哪一段、为什么，由设计方改到 `main`。任务分支只含代码 |
| `PRINCIPLES.md` | 任何人不许改 |
| `internal/protocol/` | 任务 05 定稿后锁定。要改协议 → 上报调度方 |
| `migrations/0001_init.*.sql` | 任务 04 定稿后锁定。要加表加列 → 申请新编号 |
| `.secrets/` | **永远不提交，永远不把内容写进代码、文档、日志、PR 说明** |
| `cmd/dashd/main.go` | 只允许加一行模块注册，不改装配逻辑 |
| `Makefile` | 只允许追加 target |
| 队列里其他任务的交付物目录 | ★ 不要顺手改，也不要「顺手补一个」。
任务 03 就因为自己写了任务 02 的 `internal/config` 和 `internal/logx`，
用了不同的 TOML 库，导致两个分支硬冲突 |

## 6. 跟设计冲突时

**先停下，不要边做边改设计。**

1. 在 PR 或反馈里说清楚：设计文档哪一段、为什么行不通、你建议怎么改、代价是什么
2. 等调度方确认
3. 确认后**先改 `docs/`，再改代码**（P1）

**绝对不允许**：代码按自己的想法写了，文档留着旧的。这是 P1 的核心，验收会逐项比对文档和代码。

## 7. 提交与 PR

- 一个任务一个分支：`agy/T04-migrations`
- 提交信息：`T0.3: 增加 metric_series 的唯一索引` —— 带任务号
- **PR 说明必须包含**：
  1. 权威定义里「验收」那一段的**逐条**验证方式和实际结果（贴命令和输出，不要只写「已验证」）
  2. 改了哪些设计文档（没改就写「无」）
  3. 新增了哪些第三方依赖及理由（没有就写「无」）
  4. 已知的遗留问题

## 8. 验收流程

**验收结果直接写回任务文件的「验收记录」一节**，不另开文档。

1. 每轮验收在任务文件末尾追加一节：`## 第 N 轮 · 日期 · 结论`
2. 结论分三块：
   - **✅ 已通过** —— 逐项列出实测结果。**这些不要再动**，改了要整体重验
   - **❌ 必须修** —— 编号 `F1` `F2`…，每条给出复现方式和具体修法
   - **⚠️ 顺手改** —— 不阻塞合并，但这轮一起处理掉
3. 附「复验方式」：可直接粘贴执行的命令
4. 修完后**在同一个文件里追加下一轮**，不覆盖上一轮记录
5. **直到全部通过为止**，任务文件本身就是这个任务的完整履历

对 AGY 的要求：
- 收到打回时，**只修被列出的项**。已通过的部分不要顺手重构
- 修完在 PR 说明里逐条对应 `F1` `F2`… 说明改了什么、怎么验证的

## 9. 交付前自查

提 PR 前自己过一遍，任何一条不过就别提：

- [ ] `make lint test` 通过
- [ ] 权威定义里的「验收」逐条实际跑通了，不是「应该没问题」
- [ ] 没碰第 5 节列的文件
- [ ] 改了表结构 → 同步改了 `docs/02-database.md` 和 `migrations/`
- [ ] 改了协议 → 同步改了 `docs/04-protocol.md` 并升了版本号
- [ ] 新建的目录有 `README.md`（职责边界、对外接口、依赖谁）
- [ ] 日志里翻不到任何机密
- [ ] 只做了自己这一个任务
