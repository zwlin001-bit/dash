# 通用工程约定

**每个任务都适用。派发时不再重复，但验收时逐条检查。**

---

## 1. 语言与版本

- Go **1.22+**，`go.mod` 里锁定一个具体版本，不许各任务各改
- 前端用 TypeScript
- **代码注释、提交信息、PR 说明用中文**；标识符、字段名、错误码、日志 key 用英文
- 文档用中文

## 2. 依赖纪律

**这个工程的价值有一半在「轻」上，依赖必须克制。**

- **agent 侧（`agent/`、`cmd/dash-agent`）：新增任何第三方依赖都要先上报，不许自行引入。**
  目前允许的只有 WebSocket 库一个。**gopsutil 及同类库是明令禁止的**
- 服务端新增依赖要在 PR 说明里写明：为什么标准库做不到、评估过哪些替代
- 不引入「为了少写十行代码」的工具库
- 依赖必须锁定具体版本，不用 `latest`

## 3. 测试

- 每个任务至少覆盖：**正常路径 + 一个失败路径 + 一个边界条件**
- 解析类代码（`/proc`、协议、SQL 构造）必须有单元测试，**用真实样本数据**
  （比如 Alpine 上真实的 `/proc/meminfo`，不要自己编一个理想格式）
- 涉及数据库的测试跑在独立的测试数据库上（`make test-db-up` 启动临时 MySQL 8 容器，端口 33306；`make test-db-down` 停止并清理），Oracle 侧至少手工验证一次并在 PR 里贴输出
- `make test` 自动依赖 `test-db-up` 并设置 `DASH_REQUIRE_TEST_DB=1`，任何缺少测试库导致的跳过均视为失败；本地单测若缺失测试库会输出醒目警示
- **新增 `t.Skip` 必须说明充分理由**：严禁无理由或静默跳过，跳过说明必须明确前置依赖或环境原因（`make lint` 会自动校验 `t.Skip` 纪律）
- **不追求覆盖率数字**，追求「这个 bug 会不会被测试抓到」
- `make test` 必须能在干净环境一条命令跑完

## 4. 日志与错误

- 日志写 stderr，结构化（key=value 或 JSON），**不自己做文件轮转**
- **日志和错误信息里永远不出现**：密码、token、wallet 密码、主密钥、云厂商 AK/SK。
  统一走 T0.4 提供的 redact 辅助函数
- 错误一律 `fmt.Errorf("...: %w", err)` 包装，保留链路
- **不允许吞掉错误**（`_ = doSomething()`）。确实要忽略的，写注释说明为什么

## 5. 不许碰的文件

| 文件 | 说明 |
|---|---|
| **`docs/` 下的全部文件** | ★ **AGY 一律不提交。** 需要改设计就在 PR 说明里写清楚要改哪一段、为什么，由设计方改到 `main`。任务分支只含代码 |
| `PRINCIPLES.md` | 任何人不许改 |
| `internal/protocol/` | 任务 05 定稿后锁定。要改协议 → 上报调度方 |
| `migrations/0001_init.*.sql` | 任务 04 定稿后锁定。要加表加列 → 申请新编号 |
| `.secrets/` | **永远不提交，永远不把内容写进代码、文档、日志、PR 说明** |
| `cmd/dashd/main.go` | 只允许加一行模块注册，不改装配逻辑 |
| `Makefile` | 只允许追加 target |
| 队列里其他任务的交付物目录 | ★ 不要顺手改，也不要「顺手补一个」。
任务 03 就因为自己写了任务 02 的 `internal/config` 和 `internal/logx`，
用了不同的 TOML 库，导致两个分支硬冲突 |

## 6. 跟设计冲突时

**先停下，不要边做边改设计。**

1. 在 PR 或反馈里说清楚：设计文档哪一段、为什么行不通、你建议怎么改、代价是什么
2. 等调度方确认
3. 确认后**先改 `docs/`，再改代码**（P1）

**绝对不允许**：代码按自己的想法写了，文档留着旧的。这是 P1 的核心，验收会逐项比对文档和代码。

## 7. 提交与 PR

- 一个任务一个分支：`agy/p1-04-migrations`
- 提交信息：`P1-04: 增加 metric_series 的唯一索引` —— 带任务号

### ★ 改了前端就必须重建内嵌产物

前端通过 `//go:embed dist` 打进 `dashd` 二进制。
**改了 `web/src/` 就必须跑 `make build-web`**，把产物更新进 `internal/api/dist/` 并一起提交。

只改源码不重建，编译出来的二进制里还是旧前端——代码看着修好了，部署上去毫无变化。
任务 23 就是这么被骗过去的：改了 8 个源文件，产物停在两周前，线上白屏依旧。

提交前自查：`grep -c "<你这次改动里的特征字符串>" internal/api/dist/assets/*.js` 必须命中。

### ★ 新增或修改 API 端点必须履行的两处登记义务

新增或修改任何 HTTP API 端点时，**必须同时完成两处登记**，缺少任何一处会被 `make lint` 拦截或在契约测试中暴露：

1. **登记对账表**：在 `docs/12-api-spec.md` §10 的对账表中追加/更新行，逐字段核对并记录服务端实际返回结构、前端声明类型与对齐状态。
2. **登记契约 fixture 并更新**：在 `cmd/gen-fixtures/main.go` 中注册该端点（每个列表端点必须包含「有数据」与「空数据」两份 fixture，空列表必须返回 `items: []` 而非 `null`），然后运行 `make fixtures` 生成固化 fixture。`make lint` 中的 `lint-fixtures` 守卫会自动校验 fixture 是否与服务端实现严格一致，防止服务端响应发生未察觉的漂移。

### ★ 任务完成必须自己推送分支

```sh
git push -u origin <你的分支名>
```

**这是交付的一部分，不是可选动作。**

只提交到本地就等于没交付 —— 验收方在远端看不到你的代码。
历史上任务 18、19、20 都出现过「本地已提交但没推」，
只能靠人逐台机器 ssh 去翻，浪费了三轮往返。

- **不要依赖别人跑 `up` 帮你推**
- 推完自己确认一次：`git log --oneline -1 origin/<你的分支名>` 能看到你的提交
- 分支已存在于远端且被打回过，修完同样要再推一次
- **PR 说明必须包含**：
  1. 权威定义里「验收」那一段的**逐条**验证方式和实际结果（贴命令和输出，不要只写「已验证」）
  2. 改了哪些设计文档（没改就写「无」）
  3. 新增了哪些第三方依赖及理由（没有就写「无」）
  4. 已知的遗留问题

## 8. 验收流程

**验收结果直接写回任务文件的「验收记录」一节**，不另开文档。

1. 每轮验收在任务文件末尾追加一节：`## 第 N 轮 · 日期 · 结论`
2. ★ **结论只有两种：`✅ 通过` 或 `❌ 不通过`。**
   没有「有条件通过」「基本通过」「通过但…」。
   **只要还有任何一处需要改，就是不通过。**
3. 正文分两块：
   - **✅ 已通过** —— 逐项列出实测结果。**这些不要再动**，改了要整体重验
   - **❌ 必须修** —— 编号 `F1` `F2`…，每条给出复现方式和具体修法
4. ★ **所有需要修改的内容，一律写进任务书**，不散落在对话或 PR 评论里。
   任务书是这个任务的唯一事实来源
5. 附「复验方式」：可直接粘贴执行的命令
6. 修完后**在同一个文件里追加下一轮**，不覆盖上一轮记录
7. **直到判定为「通过」为止**，任务文件本身就是这个任务的完整履历
8. 通过后由设计方合并回 `main`，并在记录末尾标注「已合并 `<commit>`」

**依赖别的任务才能验的项**（例如传输层要等服务端存在才能做断网演练）
不算缺陷，单列成「待联调补验」清单，不影响本轮判定为通过。

对 AGY 的要求：
- 收到打回时，**只修被列出的项**。已通过的部分不要顺手重构
- 修完在 PR 说明里逐条对应 `F1` `F2`… 说明改了什么、怎么验证的


## ★ 借鉴外部项目时的硬性安全约束

从任何外部项目（aliyun-guard 等）借鉴代码时：

1. ★ **只借鉴思路与算法，不整段搬运。** 搬来的代码必须逐行读懂再改写。
   看不懂的行**一律删掉**，不要"先留着反正能跑"。
2. ★ **绝不携带任何第三方 URL 进仓库。** 包括但不限于：
   CDN 链接、统计/埋点端点、字体与图标外链、示例 API 地址、
   作者的接口反代地址、`raw.githubusercontent.com` 之类的下载源。
   **一个恶意或被接管的外链就足以把凭据和账单数据送走。**
3. ★ **不许 `curl | sh`、不许运行时下载任何东西。**
   agent 与 provider 的升级一律由服务端托管产物 + sha256 校验（`PRINCIPLES.md` P3.9）。
4. 外部项目**不许**加为 submodule / go 依赖 / npm 依赖 / vendor 目录。
5. 借鉴来源与取舍结论写进任务书 §0，便于日后追溯。

**允许的出网目标只有一类**：业务本身必须调用的云厂商官方 API
（`*.aliyuncs.com`）与用户自己配置的通知端点（Telegram / Webhook）。
**这些都必须来自配置或数据库，不许硬编码在代码里。**


## 9. 交付前自查

提 PR 前自己过一遍，任何一条不过就别提：

- [ ] `make lint test` 通过
- [ ] 权威定义里的「验收」逐条实际跑通了，不是「应该没问题」
- [ ] 没碰第 5 节列的文件
- [ ] 改了表结构 → 同步改了 `docs/02-database.md` 和 `migrations/`
- [ ] 改了协议 → 同步改了 `docs/04-protocol.md` 并升了版本号
- [ ] 新建的目录有 `README.md`（职责边界、对外接口、依赖谁）
- [ ] 日志里翻不到任何机密
- [ ] 只做了自己这一个任务
- [ ] ★ 新增/改动 API 端点 → 已登记 `docs/12-api-spec.md` 对账表并在 `cmd/gen-fixtures/main.go` 登记生成 fixture（`make fixtures` 无 diff）
- [ ] ★ 改了 `web/src/` → **已跑 `make build-web` 并提交 `internal/api/dist/`**
- [ ] ★ **已 `git push -u origin <分支>`，且 `git log --oneline -1 origin/<分支>` 能看到自己的提交**
