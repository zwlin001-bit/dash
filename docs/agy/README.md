## 工作方式

- **第一期只做「监控信息 + 机器清单维护」**，19 个任务在 [`tasks/`](tasks/README.md)，
  一个文件一个任务，**按编号 01→19 顺序做**。
- **一次只做一个任务。** 不要顺手把后面的任务也做了——
  那会让验收无法定位问题，也会跟下一个派发冲突。
- 每个任务文件是自包含的（目标、交付物、约束、验收都在里面），
  设计文档只在需要背景时才翻。
- **每个任务的「验收标准」是二值的**——能跑通就是通过，跑不通就是没完成。不要交「大体上实现了」。
- **发现设计有问题**：先在 `docs/` 里改设计并写清理由，再改代码。**不要代码先跑偏、文档后补**（P1）。
- **改表结构 → 必须同时改 `docs/02-database.md` 和 `migrations/`**（P1.2）。
- **改协议 → 必须同时改 `docs/04-protocol.md` 并升版本号**（P1.3）。
- 每个 `internal/*` 和 `agent/*` 目录要有 `README.md`，写清职责边界、对外接口、依赖谁（P1.4）。

## 三条最容易被违反的红线

1. **业务代码里出现 Oracle 方言** —— `ROWNUM`、`SYSDATE`、`NVL`、`FROM dual`、`MERGE`、
   `BIGINT`、`TIMESTAMP` 列……一律不行。方言只允许出现在 `internal/db/dialect` 包和 `migrations/*.oracle.sql`。
2. **agent 引入 gopsutil 或任何重依赖** —— 资源预算是验收指标，不是建议值。
3. **迁移只写了 Oracle 一份** —— 每条迁移必须同时有 `.oracle.sql` 和 `.mysql.sql`，
   哪怕现在只跑 Oracle。这是保证可迁移性不腐化的唯一有效手段。
