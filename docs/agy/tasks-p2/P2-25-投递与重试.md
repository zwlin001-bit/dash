## 约束

- ★ **不走 Job 引擎。** `notify_deliveries` 自己就是队列：
  `delivery_state` + `attempt_no` + `next_retry_at_ms`。
  Job 引擎是给多 step 异构长任务用的，通知是单步同构高频的，塞进去是错配
- 重试 3 次，退避 **10s / 60s / 300s**，超次数标 `failed` 并产生
  `system.notify_failed` 事件
- ★ **`rendered_text` 必须存**。「为什么我没收到通知」是这类系统最常见的问题，
  存了才能一眼看出是没匹配规则、被节流、还是发送失败
- ★ **`emit()` 必须保持非阻塞。** 投递是异步消费，
  第三方挂掉绝不能影响事件写入或业务流程
- `delivery_state`：`pending` / `sent` / `failed` / `throttled` / `quiet_held`
- 免打扰时段结束时，把 `quiet_held` 的记录**合并成一条**发出
- 投递记录保留 30 天，走已有的分块清理机制
- 进程重启后，`pending` 且 `next_retry_at_ms` 已到的记录要被重新拾起

## 验收

1. 触发一次 `node.offline`，端到端收到 TG 消息
2. 断掉网络，投递失败并按 10s/60s/300s 退避重试，恢复后成功送达
3. 超过 3 次后标 `failed` 并产生 `system.notify_failed` 事件
4. **投递中途 kill dashd，重启后 pending 记录被重新拾起**，不丢不重
5. 每条投递记录里 `rendered_text` 是完整的实际发送内容
6. **停掉 TG（用错误 endpoint），业务操作全部正常**，只是通知失败
7. 被节流、被免打扰拦下的记录状态正确，免打扰结束后合并发出
