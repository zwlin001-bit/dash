# P2-26 通知配置页

> 第二期 · 任务 26 ｜ 前置：25 ｜ 分支：`agy/p2-26-web-notify` ｜ 迁移编号：无

## 目标

让配置通知这件事不用登服务器。

## 交付物

**渠道管理**：TG / webhook 渠道的增删改，**支持配多个 TG 号**；一键测试发送。

**路由规则**：事件类型（或 `xx.*` 通配）→ 选一个或多个渠道；
最低级别、节流窗口、免打扰时段。

**事件类型策略**：逐类型改级别和处置方式（`drop`/`store`/`store+ui`/`store+notify`）。
**类型本身不能新增**——事件是代码发出来的。

**模板**：列出 `/etc/dash/templates/` 下的模板，**只读展示 + 预览 + 用真实事件试发**。
不做在线编辑器——模板是文件，改文件就行。

**投递记录**：按事件、渠道、状态过滤，能看到 `rendered_text` 和失败原因。

## 约束

- ★ **机密字段只显示尾号**（`••••1234`），编辑时留空表示不修改
- ★ **「测试发送」是这个页面最重要的功能**。配完立刻能验证，
  不用等一次真实告警。测试消息要走完整链路（渲染 + 适配器），不是简单发个 hello
- 规则列表要能一眼看出「哪个类型发到哪个 TG」，这是用户配置时的主要心智负担
- 投递记录页要能直接回答「为什么我没收到」：
  没匹配规则 / 被节流 / 免打扰攒着 / 发送失败，四种情况要能区分开
- 复用第一期的组件和 API 封装，不另起一套

## 验收

1. 界面上配 2 个 TG 号 + 1 条 `node.offline` 路由到两者，测试发送两边都收到
2. 改事件类型的处置为 `drop`，该类事件不再入库
3. 模板预览能用一条真实历史事件渲染出实际文本
4. 投递记录能筛出失败的，并显示失败原因和渲染后的文本
5. 编辑渠道时留空 token，保存后原 token 未被清空

## 边界

不做模板在线编辑。
