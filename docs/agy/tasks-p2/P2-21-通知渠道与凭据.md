## 目标

**一个 TG 号 = 一条渠道记录。想配几个配几个。** 外加第一期欠下的信封加密。

## 交付物

```
migrations/0003_notify_channels.{oracle,mysql}.sql
  credentials        ★ 第一期没建，本任务补上（列定义见 02-database.md §3）
  notify_channels
internal/crypto/     信封加密：AES-256-GCM，主密钥从 /etc/dash/master.key 读
internal/notify/channel.go   渠道 CRUD + 凭据存取
internal/api/notify/         渠道管理接口
```

## 约束

- ★ **`bot_token` 绝不明文存 `notify_channels`。** 走 `credentials` 表信封加密，
  `notify_channels.credential_id` 引用它
- 主密钥 32 字节随机，存 `/etc/dash/master.key`（`0400`），**绝不入库**。
  文件不存在时由 `dashd migrate` 生成
- `config_json` 只放非机密：`chat_id` / `thread_id` / `parse_mode` / webhook 的 url 与 headers
- 渠道读取接口**返回时机密字段必须打码**，界面上只显示 `••••1234` 这种尾号
- 支持 `channel_kind`：`telegram`、`webhook`。**结构上可扩展，但本期只实现这两种**
- 表列名照第一期规范：小写、不加引号、≤30 字符、时间 `*_ms`

## 验收

1. 建 3 个不同 bot_token 的 telegram 渠道，都能正确存取
2. 直接 `SELECT` 数据库，`bot_token` 是密文
3. 重启 dashd 后仍能正确解密
4. 渠道列表接口返回里翻不到明文 token
5. 删掉 `master.key` 后启动，给出明确错误而不是 panic 或静默用空密钥
6. 两份 DDL 对比测试通过；`scripts/lint-sql.sh` 通过
